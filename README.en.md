## 🚀 Live demo

A self-contained browser build of the analyser is published at:

**https://tewei02.github.io/Real-time-Packet-Monitoring-and-Traffic-Statistics-System/**

Press **Analyse bundled capture** on that page. The browser reader dissects the bundled
200-packet capture in JavaScript and then diffs its own numbers against the output of the
Python pipeline (`docs/data/reference.json`). The *Cross-check against the Python pipeline*
panel lists every quantity compared and reports **17/17 checks passed** for the bundled
capture — the same 200 packets, 4 protocols (TCP 80, UDP 48, DNS 45, ICMP 27), identical
protocol counts and totals.

The console offers three inputs and the same reporting path for each:

| Input | What it does |
|-------|--------------|
| Bundled capture | Dissects `docs/data/demo.pcap` and cross-checks it against the Python reference. |
| Upload `.pcap` | Reads a classic libpcap file **locally in your browser**; nothing is transmitted or stored. |
| Synthetic stream | Generates a seeded simulated dataset in the browser, labelled *simulated* in the interface and in the exported report. |

It also renders the protocol donut, the top-destination bars and the packet-rate line chart,
shows the dissected packet table with a text filter, exports CSV and a Markdown report, and
registers a service worker so the page works offline and can be installed to a home screen.

### Honest labelling

- The 200 packets in `docs/data/demo.pcap` are **synthetic**, generated by this project's own
  demo generator. Addresses, ports and DNS names are fabricated.
- The *synthetic stream* button produces a **further simulated** dataset from a fixed seed. It
  is not a capture and no traffic was measured from a live network.
- Uploaded files are parsed locally in the browser; no data leaves the machine.
- No measurement results, participant counts or field-trial data are reported anywhere in this
  project; the statistics shown are exactly the properties of the capture being analysed.
- The figures in *Measured performance* describe this tool's own pipeline on captures it
  generates, on the machine recorded in `docs/data/benchmark.json`. They are performance
  measurements of the software, not measurements of any network.

## Project Overview

This is a network and communication engineering project written entirely in Python 3.11+. It
demonstrates how raw packet data can be captured, parsed, and translated into structured
statistics and visualizations — without relying on any external network monitoring service.

The system is organized around a **dual-mode architecture**: an *offline* mode that reads
standard `.pcap` files for reproducible analysis, and a *live* mode that sniffs a real network
interface (root/Administrator required) with automatic fallback to a synthetic demo dataset when
privileges are insufficient. This design keeps the project runnable on any development machine
while still supporting real network capture when conditions allow.

Core capabilities include multi-layer **protocol dissection** (Ethernet → IPv4 →
TCP/UDP/ICMP/DNS/HTTP), **flow-level traffic statistics** (packets per second, protocol
distribution, top-N talker rankings), a **Rich CLI dashboard**, and structured **data export**
(CSV, PNG charts, Markdown report). The entire pipeline requires no database or external
service — all state is held in memory as a pandas DataFrame.

A third surface, the **browser console** in `docs/`, reimplements the parser and the statistics
in JavaScript so that the same analysis can be inspected without installing anything. Keeping a
second implementation honest is itself a design goal: the console reports its own numbers side
by side with the Python reference and flags any disagreement. The same page also carries a
**Measured performance** section that renders `docs/data/benchmark.json` — where the pipeline
spends its time — as a stacked chart and a table, so the figures are visible without opening the
JSON.

## 📋 Project Background and Motivation

This project started from curiosity about "what network traffic actually is." While taking a computer-networks course, I became theoretically familiar with the TCP/IP model, the packet formats of each protocol, and the transmission mechanisms, but never had a hands-on opportunity to actually "see" packets. This system was built to answer that need — the goal is to genuinely open every packet flowing across a network with code, dissect its header fields layer by layer, and extract quantifiable traffic characteristics from it.

By design, the system deliberately emphasizes two aspects: **real-time packet inspection** and **traffic profiling**. The former lets us understand the structure of a packet at the instant of transmission (source/destination IP, protocol type, port numbers, TTL, etc.); the latter lets us observe traffic trends over time — for example, the rise and fall of packets-per-second (PPS), the distribution of protocol shares, and when peak traffic occurs. The combination of the two is exactly the core design philosophy of modern network monitoring systems such as Wireshark, Zeek, and ntopng.

This project is also an exercise in systems-design thinking: how do you decompose complex network data into manageable modules? How do you keep the program runnable across different operating systems and privilege environments? How do you make analysis results readable to non-technical audiences? Working through these questions deepened my understanding of the boundary between **networked systems** and **communication engineering**, and laid the foundation for going further in network measurement and traffic analysis.

## ✨ Technical Highlights

- **Dual-mode architecture** — supports both offline `.pcap` analysis and live interface capture (`--mode offline` / `--mode live`), with automatic fallback when system privileges are insufficient.
- **Multi-layer protocol dissection** — parses packets from Ethernet frame through IPv4 header down to TCP/UDP/ICMP payload; detects DNS query names and HTTP method verbs from raw bytes.
- **Flow-level statistics** — aggregates per-packet data into time-series metrics including PPS (packets per second), peak traffic timestamps, protocol distribution ratios, and top-N talker rankings.
- **Browser console with a verification contract** — a second, independent implementation of the reader and the aggregator runs in the browser, exposes a machine-readable status object (`window.RPM.status()`), and diffs its results against the Python reference on every load.
- **Lightweight network observability** — the entire pipeline runs without a database or external service; all state is held in-memory as a pandas DataFrame, keeping the system portable and self-contained.
- **Rich CLI dashboard** — real-time terminal output using the `rich` library renders colored tables, summary panels, and multi-column layouts without a GUI dependency.
- **Structured data export** — every analysis session can export a CSV (raw packet data), two PNG charts, and a Markdown summary report with a single `--export` flag; the browser console exports the same CSV and Markdown from page state.
- **Typed, testable design** — packets are parsed into a typed `ParsedPacket` dataclass; the suites under `tests/` cover dissection, aggregation and capture loading (32 pytest cases).
- **Offline-capable static console** — `docs/` ships a `manifest.json`, a service worker and icons, so the published page installs as a PWA and reloads without a network connection.
- **Measured, not asserted, performance** — `tools/benchmark.py` times each pipeline stage on
  captures the project generates itself and writes `docs/data/benchmark.json`; the console renders
  it directly, so the numbers on the page cannot drift from the file.

## 📊 Measured performance

`tools/benchmark.py` measures the cost of **this tool's own pipeline**. It is
deliberately narrow: no network traffic is captured or measured, and no figure
below describes a real network. The inputs are captures the script generates
itself from a fixed seed, plus the committed `sample_data/demo.pcap`.

```bash
python tools/benchmark.py            # measure and write docs/data/benchmark.json
python tools/benchmark.py --quick    # smaller sizes, for a quick check
```

Median of 5 runs on Apple M3 (8 cores), Python 3.14.5. The environment is
recorded in [`docs/data/benchmark.json`](docs/data/benchmark.json) next to the
figures, so a reader can judge comparability.

| Packets | Load | Parse | DataFrame | Statistics | Analysis total | Analysis pkt/s | Export (charts) |
|--------:|-----:|------:|----------:|-----------:|---------------:|---------------:|----------------:|
| 200 | 0.0139 s | 0.0042 s | 0.0006 s | 0.0015 s | 0.0202 s | 9,878 | 0.0904 s |
| 1,000 | 0.0723 s | 0.0198 s | 0.0020 s | 0.0017 s | 0.0958 s | 10,443 | 0.0923 s |
| 5,000 | 0.4766 s | 0.1357 s | 0.0147 s | 0.0033 s | 0.6304 s | 7,931 | 0.1345 s |
| 20,000 | 2.6128 s | 0.5586 s | 0.0536 s | 0.0125 s | 3.2375 s | 6,178 | 0.2899 s |

Peak traced memory at 20,000 packets: **109.75 MB** (≈5.5 KB per packet).

What the numbers actually say — including the parts that are unflattering:

- **Capture loading dominates, and that is where the ceiling is.** At 20,000
  packets, loading is 2.61 s of the 3.24 s analysis total (81%). Parsing is
  0.56 s, and *everything after parsing* — DataFrame construction and all the
  statistics — is under 0.07 s combined. Rewriting the aggregator would move
  almost nothing; the cost is Scapy dissecting each frame on read.
- **Throughput is not flat.** It rises to ~10.4k packets/s near 1,000 packets
  and falls to ~6.2k at 20,000, because the load stage scales worse than
  linearly while the parser does not.
- **Chart export costs roughly as much as analysing 1,000 packets** (0.09–0.29 s).
  That is why `--export` is a separate flag rather than the default.
- **Memory is linear** at ≈5.5 KB per packet, so the current in-memory design
  extrapolates to roughly 5 GB for a 1M-packet capture — it would not fit. This
  is an extrapolation from two measured points, not a measured limit.

Absolute times depend on the machine; the scaling behaviour and the load-stage
finding are the parts that carry over.

## 🛠️ Installation

### Prerequisites

- Python 3.11+
- (Linux/macOS live capture) `libpcap`: `sudo apt install libpcap-dev`
- (Windows live capture) [Npcap](https://npcap.com/)
- (optional, only for `tools/check_demo.py`) Google Chrome and `pip install -r requirements-dev.txt`

### Setup

```bash
# 1. Clone the repository
git clone https://github.com/TeWei02/Real-time-Packet-Monitoring-and-Traffic-Statistics-System.git
cd Real-time-Packet-Monitoring-and-Traffic-Statistics-System

# 2. Create a virtual environment (recommended)
python -m venv venv
source venv/bin/activate      # Linux/macOS
# venv\Scripts\activate       # Windows

# 3. Install dependencies
pip install -r requirements.txt
```

## 🚀 Usage

### Demo Mode — fastest way to try the system, no pcap file required

```bash
python main.py --demo
```

Automatically generates `sample_data/demo.pcap` with 200 synthetic packets and runs a full analysis.

### Offline Analysis Mode

```bash
# Basic analysis
python main.py --mode offline --pcap sample_data/demo.pcap

# Full analysis with all exports (CSV + charts + Markdown report)
python main.py --mode offline --pcap sample_data/demo.pcap --export

# Analyse only the first 100 packets
python main.py --mode offline --pcap sample_data/demo.pcap --limit 100
```

### Live Capture Mode

```bash
# Linux / macOS (requires root)
sudo python main.py --mode live --iface eth0 --limit 200

# Windows (run as Administrator)
python main.py --mode live --iface "Wi-Fi" --limit 200

# Let Scapy choose the default interface
sudo python main.py --mode live
```

If permission is denied, the system automatically falls back to `demo.pcap` rather than crashing.

### Browser Console (local)

```bash
python3 -m http.server 8000
# then open http://127.0.0.1:8000/docs/
```

The console is a plain static site — no build step and no bundler.

## 🔭 Design Targets and Future Directions

The following are **design targets and planned work** — they are not implemented, and no
results are claimed for them:

1. **Anomaly Detection** — planned rule-based IP flood / port scan detection.
2. **Server-side Web UI** — a FastAPI + WebSocket dashboard for multi-source, long-running capture; today's browser console is static and reads one capture at a time.
3. **Long-term Storage** — planned Elasticsearch + Kibana integration for historical trend analysis.
4. **IPv6 Support** — extend the dissector to IPv6 headers; currently IPv6 frames are counted as `OTHER` and not dissected.
5. **Deep Packet Inspection** — planned integration with Zeek or Suricata for payload-level analysis.
6. **TCP Stream Reassembly** — reconstruct TCP sessions for full HTTP body parsing.

## ⚠️ Known Limitations

- Live capture requires root / Administrator privileges; the browser build cannot capture from an interface at all.
- Scapy on Windows requires Npcap; consider pyshark as an alternative if installation is difficult.
- Only IPv4 traffic is fully parsed; IPv6 packets are labelled `OTHER` and not yet dissected.
- The bundled `demo.pcap` is synthetic and does not represent real-world traffic distributions; its addresses, ports and DNS names are fabricated.
- IP fragments are dissected but not reassembled, so fragment offsets are not reflected in the aggregates.
- HTTP detection matches request and status lines at the start of a TCP payload; it is not a full HTTP parser.
- The browser reader accepts classic `.pcap` only; `.pcapng` files are rejected with a message.
- Statistics describe packet headers only — no payload reconstruction, no session reassembly, and no inference about user identity, content or application category.
